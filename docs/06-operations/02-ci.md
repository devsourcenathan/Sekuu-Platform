> **Dernière mise à jour :** Août 2026

`.github/workflows/ci.yml`, sur chaque poussée vers `main` et chaque pull

---

# 1. Pourquoi elle existe

501 tests qui ne tournent qu'à la demande protègent **moins qu'ils n'en donnent
l'impression**. Ils créent la confiance sans la vérifier.

---

# 2. L'ordre des étapes est délibéré

| Étape | Ce qu'elle protège |
| --- | --- |
| Identifiants neutralisés | Qu'aucun test ne parte vers un vrai fournisseur |
| Style (Pint) | Rapide, échoue tôt |
| Contrats OpenAPI | Qu'aucune route ne soit non documentée, ni documentée sans exister |
| Architecture | Que Payments n'importe pas Billing, et les clés étrangères inter-modules |
| Suite complète | Le reste |
| `composer audit` | Les dépendances vulnérables |

**Le contrôle d'isolation passe en premier**, avant qu'un seul test ne
s'exécute. `phpunit.xml` neutralise les identifiants des fournisseurs, mais rien
ne le vérifiait avant l'exécution — et ce dépôt a déjà envoyé une centaine de
vrais emails le jour où une clé a été renseignée.

Les trois contrôles suivants sont extraits de la suite complète pour une raison
pratique : quand ils échouent, on veut le savoir en trente secondes et lire une
sortie courte, pas la chercher dans 501 tests.

---

# 3. PostgreSQL, jamais SQLite

Le schéma repose sur des index uniques **partiels**, des contraintes `CHECK` et
`citext`.

Une suite verte sur SQLite ne prouverait rien de ce qui protège l'argent :
l'unicité « une seule intention vivante par objet payable » — le garde-fou
anti-triple-clic — est un index partiel PostgreSQL. SQLite l'ignorerait
silencieusement, et le test passerait.

Redis est également un service du workflow : la file porte les webhooks
sortants.

---

# 4. Ce qu'elle ne fait pas

**Elle ne déploie pas.** Le déploiement touche à des identifiants de paiement
réels ; l'automatiser demande une décision distincte, et un `CredentialGuard`
qui échoue au démarrage rend un mauvais déploiement bruyant plutôt que
silencieux.

**Elle ne mesure pas la couverture.** Un pourcentage rassure sans rien dire de
ce qui est réellement protégé. Ce que la suite garantit est décrit dans
[RECAP § 5](../RECAP.md).

---

# 5. Ce qu'elle a déjà trouvé

**Le dépôt tel qu'il se clone ne pouvait pas exécuter sa propre suite.**
`phpunit.xml` déclare `tests/Unit`, un répertoire vide — et Git ne versionne pas
les répertoires vides. Toute la suite échouait sur un clone frais, avant même le
premier test, avec `Test directory not found`.

Invisible en local, où le répertoire existe depuis l'installation. C'est
exactement la classe de défaut qu'une CI existe pour attraper : ce qui marche
sur la machine de celui qui a écrit le code.

---

# 6. Reproduire un échec en local

```bash
docker compose up -d
composer install
cp .env.example .env && php artisan key:generate
php artisan test
```

L'environnement est le même : PostgreSQL 18, Redis 7, PHP 8.3.
